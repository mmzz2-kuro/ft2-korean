# 로드 후 처리 함수 조사

## 목적

리소스 로더 xref에서 대사/스크립트 후보가 바로 나오지 않았기 때문에, 로드된 데이터가 어떤 후처리를 거쳐 화면/버퍼로 넘어가는지 조사했다.

사용 도구:

- `scripts/disasm-exe-range.js`: EXE RAM 주소 기준 MIPS 명령 덤프.
- `scripts/scan-exe-xrefs.js`: 특정 함수 호출자와 상수 인자 요약.
- `scripts/scan-call-args.js`: 특정 `jal` 호출 직전의 `a0..a3` source와 주변 문맥 요약.

실행 예:

```powershell
node scripts\disasm-exe-range.js ps1\SLPS-01903\SLPS_019.03 0x80188118 0x180
node scripts\scan-exe-xrefs.js ps1\SLPS-01903\SLPS_019.03 --summary --target 0x80188118 --target 0x8018815c --target 0x801881c4
```

## Endian 변환 계층

`0x80188104..0x80188274` 근처 함수들은 텍스트 엔진이 아니라, DAT에서 읽은 big-endian 성격의 리소스를 PS1 런타임에서 쓰기 좋게 바꾸는 후처리 계층으로 보인다.

| 함수 | 호출 수 | 판정 |
| --- | ---: | --- |
| `0x80188104` | 내부 호출 | 4바이트 안의 halfword 2개 위치를 교환한다. |
| `0x80188118` | 18 | 버퍼를 2바이트 단위로 byte-swap한다. |
| `0x8018815C` | 7 | 버퍼를 4바이트 단위로 byte-swap한다. |
| `0x801881C4` | 78 | `be-hdr` 그래픽 리소스 표준 후처리. 첫 16바이트 header를 32-bit swap하고, `header[0x0C] - 0x10`만큼 payload를 16-bit swap한다. |
| `0x801881FC` | 1 | 고정 `0x4000` bytes를 16-bit swap한다. |
| `0x8018821C` | 1 | 첫 `0x30` bytes를 32-bit swap한 뒤, stride 8로 2042개의 16-bit 값을 swap하는 특수 포맷. |
| `0x80188274` | 1 | 첫 word count를 32-bit swap하고, `count * 28` bytes를 16-bit swap한 뒤 각 28-byte record 안의 두 halfword pair를 추가 교환한다. |

`0x801881C4`가 가장 많이 호출되며, 직접 상수 ID 대부분이 그래픽성 `be-hdr(width,height,payload,...)` 리소스였던 점과 맞는다.

## 표시/전송 계층 후보

후처리 뒤 자주 이어지는 함수도 일부 확인했다.

| 함수 | 판정 |
| --- | --- |
| `0x8017AB14` | `be-hdr` 데이터에서 좌표/타일 인덱스처럼 보이는 값을 읽어 별도 버퍼에 재배치한다. 내부에서 `0x8017A5EC`를 반복 호출한다. |
| `0x8017B0EC` | `x,y,w,h`류 인자를 받아 `x*4+768`, `y*8`, `w*4`, `h*8` rect를 만들고 `0x8016C7A0`를 호출한다. 호출 59개 대부분이 좌표/크기 상수 또는 마스크된 좌표를 넘기므로 짧은 VRAM rect 전송/클리어 래퍼로 본다. |
| `0x8017B13C` | 1bpp 마스크를 `0x80019000` 계열 작업 버퍼에 펼친 뒤 `0x8016C8C8`, `0x8017A6E4`로 전송한다. 직접 호출은 `0x801AD230` 래퍼 1개뿐이다. |
| `0x8017B500` | 1bpp 소스 bytes를 읽어 bit 값에 따라 두 색상 byte를 `0x8001D000` 작업 버퍼에 풀고 `0x8016C8C8`로 rect 전송한다. |
| `0x8017B2BC` | 숫자/문자 코드열을 16행 단위 8픽셀 폭 마스크로 변환한다. 입력 byte가 `0x0A`이면 `0xFF`를 쓰고, 아니면 `fontBase + row*16 + code`에서 glyph byte를 읽는다. |
| `0x801AD230` | `0x8017B13C`의 얇은 래퍼. 추가 stack 인자로 소스 포인터와 색상 byte를 전달한다. 호출자는 17개이며 주로 UI 숫자/아이콘 마스크를 그린다. |
| `0x801AD270` | 정수를 십진 자리로 분해해 임시 byte열을 만들고 `0x8017B2BC`와 `0x801AD230`으로 렌더링한다. 호출 53개. 대사 텍스트가 아니라 숫자 표시 루틴으로 보인다. |
| `0x8017BCC4` | halfword fill 루틴. VRAM/스크린 버퍼 초기화 또는 클리어에 쓰인다. |
| `0x8017AEA4` | `0x801DF158` 근처 4개짜리 halfword 설정 테이블을 갱신한다. |

`0x8017B0EC` 자체는 마스크를 펼치지 않는 rect 래퍼로 정정한다. 실제 1bpp 마스크 전개는 `0x8017B13C`와 `0x8017B500` 계층에 있다. 이전 동적 ID 조사에서 나온 `+829`, `+1008`, `+1074`, `+1151` 계열 0x800/0x1000 리소스는 이 계층에 공급되는 UI glyph/icon mask 또는 숫자 폰트성 데이터 후보로 남긴다.

## 1bpp UI 숫자/마스크 경로

추가로 `0x8017B13C`와 그 래퍼 호출부를 추적했다.

| 항목 | 결과 |
| --- | --- |
| `0x8017B13C` 직접 호출 | 1개. `0x801AD230` 래퍼에서만 호출된다. |
| `0x801AD230` 호출 | 17개. `a2` 폭은 `4, 8, 9, 10, 11, 14, 15, 19, 36` 등이 확인된다. `a3` 높이는 대부분 `2`, 일부 `8`이다. |
| `0x801AD270` 호출 | 53개. 자리 수 인자에 따라 최대값 `9, 99, 999, 9999, 99999`를 고르고 십진 digit byte열을 만든다. |
| `0x8017B0EC` 호출 | 59개. `a0/a1`은 좌표, `a2/a3`은 rect 폭/높이로 보이며 마스크 소스 포인터를 받지 않는다. |
| `1151..1169` 리소스 | `0x801AD190`/`0x8017B500` 경로에서 256x64 1bpp UI mask로 쓰인다. `scripts/preview-fs2-1bpp.js`에서 `--bytes-per-row 32 --rows 64`로 확인했다. |

따라서 현재 확인한 1bpp 경로는 대사 문자열 렌더러보다는 숫자/아이콘/짧은 UI 표기 렌더러에 가깝다. 한글화 관점에서는 UI 숫자와 아이콘은 별도 그래픽/폰트 패치 대상으로 분리하고, 대사 본문은 별도 스크립트/이벤트 reader를 계속 찾아야 한다.

## 현재 판정

- `0x80188118/5C/C4/FC/21C/274`는 텍스트 디코더가 아니라 endian/record 변환기다.
- 직접/동적 리소스 ID 경로에서 보인 `be-hdr` 리소스는 이 계층을 거쳐 그래픽 처리 루틴으로 넘어간다.
- 텍스트가 평문 Shift-JIS 리소스로 로드되는 경로는 아직 발견되지 않았다.
- UI에 표시되는 숫자/아이콘 일부는 1bpp 마스크 리소스와 `0x8017B13C`/`0x8017B500` 계열 함수로 찍히는 그래픽 문자일 가능성이 있다.
