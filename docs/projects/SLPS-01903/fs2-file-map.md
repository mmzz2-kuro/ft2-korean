# FS2_FILE.DAT 구조 조사

## 2026-06-30 정정: 확장 range는 폰트가 아니라 초상/표정 이미지

`0x8017C6F4 -> 0x8017C4F0 -> 0x80188090` 경로가 참조하는 17개 확장
range는 일본어 폰트/글리프가 아니라 캐릭터 초상/표정용 rectangle chunk로
재분류한다. `tmp/SLPS-01903/rect-page0-16bpp.html`에서 60x96 단위의
캐릭터 이미지가 확인되었다.

이 경로는 암호화된 폰트가 깨져 보이는 현상이 아니다. `0x80188090`이
6 sectors를 읽은 뒤 별도 복호화/해제 없이 `0x8016C8C8` GPU 전송 래퍼로
넘기며, 16bpp raw rectangle로 보았을 때 의미 있는 이미지가 나온다.

따라서 실제 대사/폰트 조사는 script handler 중 다른 리소스 로드 경로,
특히 `0x8017FF00`의 `resourceId = 4277 + scriptWord` 경로로 이어간다.

## 확인된 로더 경로

`SLPS_019.03` 안에서 `FS2_FILE.DAT` 접근 루틴은 다음 흐름으로 좁혀졌다.

| RAM 주소 | 파일 오프셋 | 판정 |
| --- | ---: | --- |
| `0x80187D20` | `0x1F520` | `\FS2_FILE.DAT;1` 주소를 만들어 파일 검색 함수를 호출하는 초기화 지점 |
| `0x801882F4` | `0x1FAF4` | CD 파일 검색 함수 후보. 경로 첫 문자가 `\`인지 검사하고 경로 조각을 처리한다 |
| `0x80179884` | `0x11084` | CD 위치 3바이트를 BCD에서 LBA로 변환하는 함수로 보인다 |
| `0x80187D4C` | `0x1F54C` | 리소스 ID의 byte size 계산: `(table[id + 1] - table[id]) << 11` |
| `0x80187D84` | `0x1F584` | 리소스 ID와 목적지 주소를 받아 DAT 섹터 읽기를 큐잉한다 |
| `0x80187A64` | `0x1F264` | 실제 섹터 읽기 큐 등록 함수 후보. 파일 LBA base에 DAT 내부 sector offset을 더해 읽는다 |
| `0x80187B8C` | `0x1F38C` | 큐에 남은 DAT 섹터 읽기를 flush/wait하는 함수 후보 |

`0x80187A64`는 `gp+0x250`에 저장된 `FS2_FILE.DAT`의 base LBA에 내부 sector offset을 더하고, CD read 계열 함수 `0x80179970`을 호출한다. 인자는 대략 목적지 주소, 시작 sector, sector count로 보인다.

## 섹터 오프셋 테이블

EXE의 `0x801C4F68`에는 `FS2_FILE.DAT` 내부 sector offset 테이블이 있다.

- RAM 주소: `0x801C4F68`
- EXE 파일 오프셋: `0x5C768`
- 값 형식: `u16 LE` sector offset
- sector 단위: `0x800` bytes

첫 값은 `0, 4, 10, 13, 34...`이며, DAT 안의 시작 오프셋 `0x0`, `0x2000`, `0x5000`, `0x6800`, `0x11000...`와 일치한다.

### 일반 리소스 테이블

현재 해석:

- 일반 리소스 ID: `0..4449`
- 경계 값: `table[0..4450]`
- 일반 리소스 테이블이 가리키는 DAT byte range: `0x0..0x3A7E000`
- size 공식: `(table[id + 1] - table[id]) * 0x800`

초기 리소스 샘플:

| ID | sector | DAT 오프셋 | 다음 오프셋 | span | 헤더 |
| ---: | ---: | ---: | ---: | ---: | --- |
| 0 | 0 | `0x0` | `0x2000` | `0x2000` | `37, 3, payload=0x1B10, 0x2F0` |
| 1 | 4 | `0x2000` | `0x5000` | `0x3000` | `28, 6, payload=0x29D0, 0x360` |
| 2 | 10 | `0x5000` | `0x6800` | `0x1800` | `25, 4, payload=0x1250, 0x2D8` |
| 3 | 13 | `0x6800` | `0x11000` | `0xA800` | `28, 23, payload=0xA0D0, 0x718` |
| 4 | 34 | `0x11000` | `0x1C000` | `0xB000` | `28, 23, payload=0xA110, 0x718` |

주의: 일반 리소스 전체가 같은 16바이트 헤더 포맷은 아니다. 첫 run 안에도 다음 형식이 섞인다.

- 16바이트 big-endian 헤더 + payload + sector padding
- blank/zero chunk
- `0x00000400`으로 시작하는 raw chunk
- GPU packet 또는 그래픽 명령처럼 보이는 raw payload
- `0xFFFFFFFF` fill chunk

따라서 "리소스 ID가 있다"는 사실과 "각 리소스의 내부 포맷"은 분리해서 판정해야 한다.

## 평문 텍스트 스캔 결과

일반 리소스 `0..4449`의 경계를 기준으로 Shift-JIS 후보를 재스캔했다. 현재까지 나온 후보는 반복 패턴과 그래픽/수치 데이터가 일본어처럼 우연히 디코드된 잡음이 대부분이다.

판정:

- `FS2_FILE.DAT`의 주요 텍스트가 평문 Shift-JIS로 바로 들어 있다고 보기는 어렵다.
- 텍스트는 압축, 커스텀 스크립트 인코딩, 또는 아직 분리하지 못한 리소스 포맷 안에 있을 가능성이 높다.
- 다음 텍스트 조사는 DAT 전체 스캔이 아니라 리소스 ID/포맷별로 해야 한다.

# 2026-06-30 추가: 확장 range chunk 단위 보정

`0x80187C6C`가 만드는 17개 확장 range는 모두 `0x1B9000` bytes다. 이는
`882` sectors이고, 표시 코드표의 sentinel 제외 항목 수 `147`과 곱셈 관계가
맞는다. 현재 이 표시 코드표는 폰트가 아니라 초상/표정 코드표로 본다.

```text
0x1B9000 bytes = 882 sectors
882 sectors / 147 codes = 6 sectors per code
6 sectors = 0x3000 bytes
```

따라서 `0x80188090(index, dst)`에서 보이는 `index * 6`은 6바이트가 아니라 6섹터 단위 오프셋이다. 즉 각 확장 page는 `AA`, `AB`, `AC` 같은 코드표 index별로 `0x3000` bytes짜리 표시 chunk 147개를 담는 구조로 보인다.

추가 도구:

```powershell
node scripts\dump-fs2-extended-ranges.js ps1\SLPS-01903\SLPS_019.03 ps1\SLPS-01903\FS2_FILE.DAT
node scripts\preview-fs2-extended-glyphs.js ps1\SLPS-01903\SLPS_019.03 ps1\SLPS-01903\FS2_FILE.DAT --page 0 --start 0 --count 4 --mode bitmap --bytes-per-row 16 --rows 24
node scripts\export-fs2-extended-atlas.js ps1\SLPS-01903\SLPS_019.03 ps1\SLPS-01903\FS2_FILE.DAT tmp\SLPS-01903\extended-page0.pbm --page 0 --chunk-width-bytes 16 --chunk-rows 24 --columns 7
node scripts\export-fs2-extended-html.js ps1\SLPS-01903\SLPS_019.03 ps1\SLPS-01903\FS2_FILE.DAT tmp\SLPS-01903\extended-page0.html --page 0 --chunk-width-bytes 16 --chunk-rows 24 --columns 7 --scale 2
```

검증용 atlas:

- `tmp/SLPS-01903/extended-page0.pbm`
- `tmp/SLPS-01903/extended-page1.pbm`
- `tmp/SLPS-01903/extended-page0.html`
- `tmp/SLPS-01903/extended-page1.html`

`tmp/`는 `.gitignore` 대상이므로 원본 기반 파생 이미지 산출물은 저장소 추적 대상에 넣지 않는다.
