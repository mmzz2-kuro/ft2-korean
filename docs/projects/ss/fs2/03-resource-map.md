# 세가 새턴판 파랜드 사가 2 리소스 지도

## 범위

ISO 파일 `1`의 리소스 경계와 실행 파일 `0`의 참조 관계를 기록한다. 현재 단계에서는 리소스의 의미보다 컨테이너 접근 방식과 PS1판과의 공통/분기 지점을 우선 확정한다.

기준 위치:

| 대상 | 위치 |
| --- | --- |
| ISO 파일 `0` | LBA 21, 319,524 bytes |
| 파일 `0` RAM base | `0x06010000` |
| ISO 파일 `1` | LBA 178, 448,993,280 bytes |
| 파일 `1` 논리 섹터 | 2,048 bytes |

## 컨테이너 직접 스캔

Track 1 BIN에서 파일 `1`을 별도로 복사하지 않고 직접 조사한다.

```powershell
node scripts/ss-fs2-scan-container.js `
  "ss/others/Farland Saga - Toki no Michishirube (Japan) (Track 1).bin" `
  --compare-flat "ps1/SLPS-01903/FS2_FILE.DAT"
```

스크립트의 기본값은 파일 `1`의 확정된 위치인 LBA 178과 크기 448,993,280 bytes다.

## 리소스 섹터 테이블

실행 파일 `0`의 file offset `0x1AE9C`, RAM 주소 `0x0602AE9C`에서 big-endian unsigned 16-bit 섹터 경계 배열을 확인했다.

초기 값:

```text
0, 4, 10, 13, 34, 56, 78, 100, 122, 144,
165, 195, 198, 202, 204, 213, 228, 233, 235, 242,
248, 255, 260, 263, 302, 331, 388, 420, 461, 562,
586, 635, 665, 691, 736, 858, 905, 1077, 1118, 1159 ...
```

각 값에 `0x800`을 곱하면 파일 `1` 내부 경계가 된다. 예를 들어 초기 블록은 다음과 같다.

| 인덱스 | 섹터 | 파일 `1` offset | 다음 경계 |
| ---: | ---: | ---: | ---: |
| 0 | 0 | `0x00000` | `0x02000` |
| 1 | 4 | `0x02000` | `0x05000` |
| 2 | 10 | `0x05000` | `0x06800` |
| 3 | 13 | `0x06800` | `0x11000` |
| 4 | 34 | `0x11000` | `0x1C000` |
| 5 | 56 | `0x1C000` | `0x27000` |

컨테이너 블록의 payload 길이만 정렬한 결과와 테이블 경계가 한 섹터 차이 나는 경우가 있다. 따라서 블록 경계의 권위 있는 근거는 실행 파일의 섹터 테이블이며, 헤더 스캔의 `next` 계산값만으로 연속 블록을 확정하지 않는다.

## 테이블 참조점

RAM 주소 `0x0602AE9C`는 실행 파일의 다음 리터럴 위치에 저장되어 있다.

| 리터럴 file offset | 이 리터럴을 읽는 명령 | 명령 RAM 주소 |
| ---: | ---: | ---: |
| `0x1E6E8` | `MOV.L @(disp,PC),R1` | `0x0602E66C` |
| `0x1E720` | `MOV.L @(disp,PC),R1` | `0x0602E708` |
| `0x1E78C` | `MOV.L @(disp,PC),R1` | `0x0602E73E` |
| `0x1E894` | `MOV.L @(disp,PC),R1` | `0x0602E808` |

### `0x0602E708` 주변의 크기 계산

주요 opcode 흐름:

```text
0x0602E704  604D
0x0602E706  300C
0x0602E708  D105  ; R1 = 0x0602AE9C
0x0602E70A  021D
0x0602E70C  622D
0x0602E70E  7102
0x0602E710  011D
0x0602E712  601D
0x0602E714  3028
0x0602E716  4018
0x0602E718  300C
0x0602E71A  4008
0x0602E71C  000B
```

잠정 해석:

- 입력 인덱스를 2배 하여 u16 테이블 인덱스로 사용한다.
- 인접한 두 섹터 경계를 읽어 뺀다.
- 차이를 `0x800`배 하여 리소스 byte length를 반환한다.
- 마지막의 shift/add 조합은 `(nextSector - startSector) << 11`과 일치한다.

따라서 이 루틴은 리소스 ID에서 할당 영역 크기를 구하는 함수로 판단된다. 정확한 함수 시작 주소와 호출 규약은 추가 역어셈블이 필요하다.

`0x0602E73E`와 `0x0602E808` 주변은 같은 테이블에서 시작 섹터를 읽은 뒤 CD 읽기 또는 메모리 전송 준비로 이어지는 후보다.

## PS1판과의 공통 구간

SS판 파일 `1`과 PS1판 `FS2_FILE.DAT`의 첫 차이는 다음과 같다.

| 항목 | 값 |
| --- | ---: |
| 첫 불일치 container offset | `0x83802` |
| 섹터 | 263 |
| 섹터 내 offset | 2 |
| SS byte | `0x04` |
| PS1 byte | `0x00` |

섹터 테이블의 23번째 경계가 263이므로:

- 경계 0부터 263 직전까지, 즉 초기 리소스 0~22의 할당 영역은 byte-for-byte 동일하다.
- 리소스 23은 양판 모두 섹터 263에서 시작하지만 내용과 다음 경계가 다르다.
- SS판의 다음 경계는 302, PS1판의 다음 경계는 423이다.
- 리소스 23의 할당량은 SS판 39섹터, PS1판 160섹터다.

리소스 23 시작 32 bytes:

```text
SS : 00 00 04 00 00 00 00 00 00 00 00 00 00 00 00 00
     00 00 08 00 00 00 00 16 00 00 00 00 00 00 00 00
PS1: 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
     00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
```

이는 같은 컨테이너를 그대로 복사한 것이 아니라 플랫폼별 리소스를 같은 ID 공간에 배치한 구조임을 보여준다.

## 일반 리소스 수와 후반 range pair

초기화 함수 `0x0602E620`은 PC-relative 16-bit 상수 `0x21DE`를 읽어 테이블 byte offset으로 사용한다.

```text
0x21DE / 2 = 4335
```

이어지는 코드는 index 4335부터 17개의 시작/끝 쌍을 읽고, 다음 u16 값이 이전 값보다 작아질 때 상위값에 `0x10000`을 더한다. 반복 상수는 16이며 0부터 16까지 순회한다.

따라서 다음을 확정한다.

- 일반 리소스 수: 4,335개
- 일반 리소스 ID: 0~4,334
- 일반 경계 배열: index 0~4,335
- 대형 range pair 시작: index 4,335
- 대형 range pair 수: 17개
- index 4,335의 값은 마지막 일반 리소스의 끝 경계와 첫 range의 시작값으로 함께 사용된다.

range 사이에는 일정하지 않은 gap이 있으며 마지막 range 뒤에도 파일 `1` 끝 219,235섹터까지 데이터가 남는다. 이 gap과 tail의 용도는 아직 미확정이다.

후속 조사에서 이 gap 중 `table[4336/4337]`, `table[4338/4339]`처럼
한 칸 어긋나게 묶이는 17개 구간은 모두 882-sector zero separator임을
확인했다. 메시지 로더는 각 separator의 끝 sector를 그룹 base로 사용한다.
실제 message block은 그 뒤의 대형 range 안에서 그룹별 offset table로
선택된다. 자세한 내용은 `18-message-bank-map.md`를 참조한다.
