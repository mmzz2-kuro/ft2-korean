# Reveal count 확장 PoC

## 결론

SS판도 원문 수정, 글꼴 축소, 자간 축소 없이 reveal count를 늘릴 수 있는 실행 코드 PoC를 만들었다. 첫 시험 대상은 message `1006`이며, 원래 count `6`을 `7`로 확장해 기존 84 entry 제한을 98 entry로 늘렸다. 한국어 mask의 유효 범위는 88 entry이다.

실행용 이미지:

```text
output/ss-fs2-reveal-ext-1006.cue
output/ss-fs2-reveal-ext-1006.bin
```

## PS1판과 SS판의 차이

PS1판은 message block의 `0x930` 뒤에 고정 `0xD0`바이트 reveal 영역을 예약한다. PS1 실행 코드 `0x8017CC90`은 count에 맞춰 시작 포인터를 읽고, RAM에서 마지막 포인터를 한 번 복제한다. 따라서 고정 영역 안에서는 count를 늘려도 뒤의 미디어 데이터를 이동할 필요가 없다.

SS판은 원본 count와 경계표 바로 뒤에 다음 데이터가 이어진다. 디스크 상의 경계표를 단순 연장하면 그 데이터를 덮으므로 PS1 방식 그대로는 적용할 수 없다.

## SS 확장 방식

원본 32비트 count 필드를 다음처럼 해석한다.

```text
상위 16비트: 확장 count, 0이면 미사용
하위 16비트: SS 원본 count
```

message `1006`의 필드는 다음과 같이 바뀐다.

```text
원본: 00 00 00 06
PoC : 00 07 00 06
```

실행 파일에는 80바이트 SH-2 트램펄린을 빈 코드 영역에 넣었다.

| 항목 | 값 |
| --- | --- |
| 트램펄린 RAM 주소 | `0x0605DD40` |
| 실행 파일 offset | `0x4DD40` |
| 임시 reveal 헤더 | `0x0607B800` |
| 원래 reveal 루틴 | `0x060202A0` |
| 호출 포인터 offset | `0x103FC` |
| 헤더 포인터 offset | `0x10314` |

트램펄린은 원본 count와 `count+1`개의 경계를 임시 RAM으로 복사한다. 확장 count가 있으면 원본 마지막 경계를 필요한 수만큼 복제한 뒤 원래 reveal 루틴으로 이동한다. 상위 16비트가 0인 기존 대사는 원본 count를 사용하므로 같은 실행 파일에서 그대로 처리된다.

임시 헤더 `0x0607B800`은 출력 테이블의 최대 사용 끝과 mask 버퍼 `0x0607BC30` 사이의 확인된 빈 구간에 둔다.

## 빌드와 검증

재현 명령:

```powershell
node scripts/ss-fs2-reveal-extension-poc.js `
  output/ss-fs2-korean-safe.bin `
  output/ss-fs2-reveal-ext-1006.bin `
  1006 `
  tmp/SLPS-01903/dialogue-workflow/apply/message-mask-1006-ko.pgm
```

결과:

| 항목 | 값 |
| --- | ---: |
| 한국어 유효 entry | 88 |
| 원본 count / capacity | 6 / 84 |
| 확장 count / capacity | 7 / 98 |
| 변경 LBA | 53, 176, 30320, 30321 |
| 변경 sector 수 | 4 |
| user-data 변경 byte | 291 |
| Mode 1 EDC/ECC 오류 | 0 |

호출부 `0x060203A8`은 트램펄린 `0x0605DD40`을 가리키며, 원래 루틴의 헤더 참조는 임시 헤더 `0x0607B800`을 가리키는 것을 disassembly와 xref 검사로 확인했다. 빌드 스크립트도 출력 후 상위/하위 count, 두 실행 포인터, 주입 코드의 byte 일치를 다시 검사한다.

## 현재 PoC의 표시 특성

이번 1차 PoC는 원래 시간 경계를 보존하고 추가 경계에는 마지막 시각을 반복한다. 따라서 기존 84 entry는 원래 속도로 나타나고, 초과한 마지막 4 entry는 원래 대사의 마지막 시점에 함께 나타난다. 내용은 잘리지 않지만 초과부 reveal이 매끄럽지는 않다.

실기 또는 에뮬레이터에서 다음을 확인해야 한다.

1. message `1006`의 `갑자기... 이런...`이 일본어 잔여 없이 끝까지 표시되는가.
2. 마지막 네 entry가 마지막 시점에 나타나고 이후 진행이 멈추지 않는가.
3. 다음 대사와 음성 재생이 정상인가.
4. 확장 필드가 없는 기존 한국어 대사가 이전 빌드와 동일하게 보이는가.

이 시험이 통과하면 다음 단계에서 마지막 경계 반복 대신 전체 경계를 재분배하여 확장 부분도 일정한 속도로 드러나도록 개선하고, reveal 초과 534개 전체 manifest 생성으로 확장한다.

## 1차 실기·에뮬레이터 확인 결과

사용자 확인 결과 message `1006`은 한국어 문장이 마지막까지 표시되었다. 대사 진행과 음성이 모두 정상이었고 게임 정지나 화면 깨짐도 관찰되지 않았다. 따라서 다음 항목은 통과로 판정한다.

- 확장 count의 런타임 인식
- 초과 entry의 최종 표시
- 원래 reveal 루틴 복귀
- 다음 대사 진행과 음성 재생

다만 문장이 짧고 초과량이 4 entry뿐이어서 표시 시점의 자연스러움까지 판정하기는 어렵다.

## 2차 초반 연속 대사 시험

여러 message를 한 이미지에서 검사할 수 있도록 PoC 도구가 `<messageId> <PGM>` 쌍을 반복해서 받도록 확장했다. 다음 네 대사를 패치한 시험 이미지를 생성했다.

```text
output/ss-fs2-reveal-ext-early.cue
output/ss-fs2-reveal-ext-early.bin
```

| message | 한국어 문장 | 유효 entry | 원본 count/capacity | 확장 count/capacity |
| ---: | --- | ---: | ---: | ---: |
| 1006 | 갑자기... 이런... | 88 | 6 / 84 | 7 / 98 |
| 1011 | 뭐, 귀여운 꼬마숙녀의… | 344 | 23 / 322 | 25 / 350 |
| 1013 | 아! 아! 그런데 이곳에는… | 256 | 16 / 224 | 19 / 266 |
| 1016 | 우선은, 모험가 길드로… | 292 | 20 / 280 | 21 / 294 |

검증 결과는 변경 sector 10개, user-data 변경 2,784바이트, Mode 1 EDC/ECC 오류 0이다. 출력 SHA-256은 `AC4E1547C0A98676F5224E3940358B3A675BC065EEE5C2CC01F5DF94C8C9E3B6`이다.

2차 시험에서는 특히 message `1011`과 `1013`의 두 번째 줄 끝이 모두 표시되는지, 끝부분이 한꺼번에 나타나는 현상이 눈에 띄는지, 각 대사 뒤 음성과 진행이 정상인지 확인한다.
