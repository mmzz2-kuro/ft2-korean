# 새턴판 오프닝 캐릭터 설명 적용

## 대응 리소스

PS1 원본의 디코딩 픽셀 SHA-256을 새턴판 일반 리소스 4,335개와 전수 비교했다.
화면 크기뿐 아니라 전체 픽셀이 일치하는 대응 관계는 다음과 같다.

| 캐릭터 | PS1 ID | 새턴 ID | 크기 | 새턴 타일 용량 |
| --- | ---: | ---: | ---: | ---: |
| 아리스 | 255 | 226 | 160×240 | 453 |
| 라디슈 | 257 | 228 | 320×120 | 421 |
| 알 | 263 | 234 | 160×240 | 421 |
| 사라 | 265 | 236 | 160×240 | 325 |
| 루루 | 268 | 239 | 160×240 | 389 |
| 소피아 | 269 | 240 | 160×240 | 389 |
| 카린 | 286 | 257 | 160×240 | 453 |

이 구간은 기존 UI 이관에서 사용했던 `PS1 ID - 114` 규칙이 아니라 모두
`PS1 ID - 29`에 해당한다. 실제 결정에는 산술 규칙이 아니라 전체 픽셀 일치를
사용했다.

## 적용 이미지와 타일 용량

PS1 인게임에서 확인한 다음 최종 PGM 7개를 입력으로 사용한다.

`tmp/SLPS-01903/opening-character-workflow/gui-build/windows-ko-pgm`

6장은 고정 할당량 안에서 무손실로 패킹된다. 소피아는 431개 고유 타일이 필요하지만
새턴 리소스 240의 원래 용량은 389개이다. 최초 시험판은 상단 본문을 보호하고 하단
배경 타일 42개를 통합했으나, 배경에 들어간 회색 한글 장식이 깨져 보였다.

최종 방식은 일반 리소스 `697`, `705`의 실제 미사용 후행 공간을 각각 1섹터씩
회수하고 리소스 `240`을 13섹터에서 15섹터로 확장한다. 240~705 구간을 정적으로
재배치하고 경계 테이블을 갱신하므로 전체 아카이브 크기, 일반 리소스 끝 위치,
메시지 영역은 변하지 않는다. 확장 용량은 453타일이며 소피아의 431타일을 어떠한
근사 통합도 없이 저장한다.

카린도 PS1 시험판에서는 465타일 중 12타일을 줄여 453타일 고정 용량에 맞췄다.
이때 우측 하단의 1~2픽셀 차이 타일이 합쳐져 인게임에서 배경 일부가 뭉개졌다.
처음에는 리소스 `709`의 미사용 1섹터를 회수해 새턴 리소스 `257`을 16섹터로
확장했지만, 인게임 런타임의 카린 타일 슬롯은 453개로 고정된 것으로 확인됐다.
인덱스 453 이후가 행 우선 배치상 하단에 몰려 하단 우측이 깨져 보였다.

최종 방식은 453타일 제한을 유지하되, 카린의 전체 하단 `y >= 144`와 검은 본문
픽셀이 든 타일을 모두 보호한다. 필요한 12타일 통합은 상단의 옅은 회색 배경
장식에서만 수행한다.

## 도구와 결과

- 매핑 검사: `scripts/ss-fs2-map-opening-resources.js`
- 런타임 사본 검사: `scripts/ss-fs2-find-opening-runtime.js`
- 빌더: `scripts/ss-fs2-build-opening-profiles.py`
- 소피아 무손실 확장: `scripts/ss-fs2-expand-opening-sophia.js`
- GUI: `tools/ss_fs2_opening_character_gui.py`
- 입력: `output/ss-fs2-korean-ending-credits-expanded.bin`
- 출력: `output/ss-fs2-korean-opening-profiles.bin`
- 보고서: `tmp/ss-fs2-opening-character-workflow/gui-build/ss-opening-build-report.json`

출력 BIN을 다시 추출하여 7개 리소스가 모두 정상적인 BE-HDR 구조와 예상 크기로
디코딩되는 것을 확인했다. CUE는 기존 Track 2 오디오 항목도 유지한다.

## QA

오프닝에서 7명 화면을 차례로 확인한다. 특히 소피아 화면은 한글 글자와 함께 하단
배경에서 눈에 띄는 타일 경계나 문양 손상이 없는지 확인해야 한다.
