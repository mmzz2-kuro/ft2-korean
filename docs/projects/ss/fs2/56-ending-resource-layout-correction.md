# 엔딩 리소스 추가 확인과 크레딧 배치 보정

> 최종 정정: 아래에서 시도한 순환 이동/확장 방식은 폐기한다. 실제 원인은
> 타일맵 시작 오프셋 오판이었다. 올바른 결과와 구조는 문서 마지막의
> `최종 구조 판정`을 기준으로 한다.

## 세 번째 엔딩 문구

리소스 0, 1 외에 사용자가 확인한 세 번째 문구는 SS resource `2`이다.

- resource ID: `2`
- 컨테이너 sector: `10..12`
- 크기: `200x32`
- 원문: `現在のアトラクタへ...`
- 의미: `현재의 어트랙터로...` / 문맥상 `현재의 어트랙트로...`
- 확인 이미지: `tmp/ss-fs2-ending-audit/resource-2.png`

따라서 엔딩 선택 화면의 교체 대상은 `0`, `1`, `2` 세 개이다.

## 성우 크레딧 타일 번호 확인

resource `14`, `15`의 PNT 값 `0x0200` 이상을 세로 반전 플래그로 해석한
것은 잘못이었다. 이 값은 로컬 자료 범위 밖의 예약/외부 타일 번호이며,
로컬 tile 0으로 접어 읽으면 잘못된 글자 조각이 반복된다.

추출기를 다음과 같이 수정했다.

- tile index: `pnt >> 1`
- bit 0: 수평 반전
- resource 범위 밖 tile: 빈 타일
- `0x0200`을 로컬 tile 0으로 마스킹하지 않음

## 순환 화면 배치 보정

크레딧 화면은 폭 320의 순환 타일맵이다. resource 14와 15 모두 저장
배열의 `x=191`에 높이 약 192픽셀의 흰 세로 경계선이 있다. 처음에는 이
선을 화면 오른쪽 끝에 맞추기 위해 오른쪽으로 이동했으나, 실기 화면 확인
피드백상 뒤쪽 타일이 왼쪽 위로 넘어와 배치되는 방향이었다. 따라서 화면을
오른쪽으로 미는 방식은 폐기하고 전체 타일맵을 왼쪽으로 `128px` 당긴다.
보정 후 흰 세로선은 `x=63`에 놓이고 크레딧 본문은 선 오른쪽에 이어진다.

보정식:

```text
displayX = (storedX - 128) mod 320
```

가로 순환 이동 후 흰 세로선 오른쪽에서 넘어온 항목 블록은 나머지 이름
블록보다 정확히 한 타일 위에 놓인다. 선 자체는 유지하고 정렬 화면의
`x=64..319` 영역 전체를 아래로 `8px` 순환 이동한다. 처음 지정한
`x=64..191`은 오른쪽 절반만 포함해 `x=192` 이후 첫 글자의 윗부분이
남거나 잘리는 잘못된 영역이었다. 세로 이동도 글자가 화면 위아래 경계를
걸칠 수 있으므로 240픽셀 높이 안에서 순환시킨다.

```text
creditBlockY = storedY + 8
```

처음 적용한 `x=240` 시작점은 잘못된 추정이었으며 폐기했다.

보정 이미지:

- `tmp/ss-fs2-ending-audit/resource-14-aligned.png`
- `tmp/ss-fs2-ending-audit/resource-15-aligned.png`

화면 아래쪽의 작은 조각은 같은 순환/스크롤 타일맵에서 현재 표시 영역
밖에 놓인 인접 크레딧 내용이다. 자료 손상은 아니다. 번역 편집과 재삽입
때에는 화면 확인용으로 오른쪽 `128px` 이동하고, 저장할 때는 반대로
왼쪽 `128px` 이동해 원래 좌표계로 복원해야 한다.

## 무이동 확인본

`aligned` 방식은 사람이 보기 편하도록 순환 좌표를 재배치하므로 원본 위치
확인용으로는 적합하지 않다. 원본 좌표를 전혀 이동하지 않고 경계에 걸린
문자열 전체를 보려면 순환 사본을 캔버스 밖에 덧붙여야 한다.

- 출력 크기: `960x256`
- 중앙 원본 영역: `(320,8)..(639,247)`
- 좌우: 원본 320픽셀 순환 사본
- 상하: 원본 8픽셀 순환 사본
- 원본 320x240 픽셀의 내부 좌표 변경 없음

확인 파일:

- `tmp/ss-fs2-ending-audit/resource-14-unmoved-unclipped.png`
- `tmp/ss-fs2-ending-audit/resource-15-unmoved-unclipped.png`

이 파일은 구조 확인용이며 그대로 재삽입하는 편집 파일은 아니다. 실제
편집·삽입 파일은 가운데 320x240 원본 영역을 기준으로 해야 한다.

## 최종 구조 판정

resource 14/15의 크기는 40x30 tiles이며 타일 데이터 오프셋은 `0x970`이다.
타일맵 크기는 다음과 같다.

```text
40 * 30 * 2 = 0x960 bytes
0x970 - 0x960 = 0x10
```

따라서 이 특수 엔딩 리소스에는 일반 BE-HDR의 `0x200`바이트 내장 팔레트가
없고, 타일맵은 `0x210`이 아니라 `0x10`에서 시작한다. 이전 추출기는
`0x210`부터 읽어 타일맵 엔트리 256개를 건너뛰었다. 폭 40 기준으로
`3행 + 8열`만큼 잘못 읽은 결과가 가로·세로 밀림과 `ソフィア` 윗부분
절단으로 나타났다.

수정된 추출기는 다음 식으로 타일맵 시작점을 구한다.

```text
tileMapOffset = tileDataOffset - widthTiles * heightTiles * 2
              = 0x10
```

이 방식에서는 좌표 이동, 순환 재배치, 캔버스 확장이 필요 없다. 원본
320x240 배열을 그대로 복원했을 때 글자와 오른쪽 흰 세로선이 정상적으로
표시된다.

최종 확인 파일:

- `tmp/ss-fs2-ending-audit/resource-14-final.png`
- `tmp/ss-fs2-ending-audit/resource-15-final.png`
