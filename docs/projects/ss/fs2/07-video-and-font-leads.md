# 세가 새턴판 파랜드 사가 2 비디오 및 폰트 후보

## 범위

실행 파일 `0`에서 VDP1/VDP2 메모리 주소를 읽는 SH-2 코드를 찾고 문자 렌더러 및 폰트 후보를 좁힌다. 이번 단계의 주소는 정적 후보이며, 실제 대화 화면에서 사용된다는 판정은 에뮬레이터 실측 전까지 보류한다.

## 플랫폼 전제 정정

`Krom2RawAdd`는 PlayStation BIOS의 일본어 글리프 API다. 세가 새턴 분석에 적용할 수 없으므로 SS판 조사 계획에서는 해당 호출 탐색을 제거했다.

현재 우선순위는 다음과 같다.

1. 게임 자체 문자 코드 소비 루틴
2. 게임 데이터에 포함된 글리프/문자 그래픽
3. Work RAM에서 VDP1/VDP2 VRAM으로 향하는 전송
4. VDP2 PNT 또는 VDP1 command 생성 코드

## 확인된 비디오 주소군

실행 파일에는 다음 주소군의 PC-relative literal이 다수 존재한다.

| 주소군 | 의미 |
| --- | --- |
| `0x05C0xxxx`, `0x25C0xxxx` | VDP1 VRAM 및 캐시 스루 접근 |
| `0x25D0xxxx` | VDP1 framebuffer/관련 영역 후보 |
| `0x25E0xxxx`~`0x25E7xxxx` | VDP2 VRAM 캐시 스루 접근 |
| `0x25F0xxxx` | VDP2 CRAM |
| `0x25F800xx` | VDP2 레지스터 |

VDP1과 VDP2 경로가 모두 존재하므로 주소가 있다는 사실만으로 대화 텍스트 하드웨어를 결정할 수 없다.

## VDP2 PNT 후보 주소

다음 세부 주소는 실행 코드가 직접 읽는다.

| VDP2 주소 | MOV.L 참조 명령 |
| ---: | --- |
| `0x25E40E00` | `0x06031186`, `0x0603142A` |
| `0x25E40E24` | `0x0603455C`, `0x06034612`, `0x060346AA`, `0x060346F8`, `0x06034752` |
| `0x25E41E00` | `0x0603484E` |
| `0x25E420A0` | `0x06031E30` |

이 주소들은 `0x25E40000` 부근 map/pattern 영역의 작은 offset을 가진다. 특히 같은 함수 안에서 좌표·stride 계산과 함께 쓰이는 참조는 PNT 쓰기 또는 UI tilemap 갱신 후보다.

현재 함수 범위 후보:

| 참조 묶음 | 함수 범위 후보 |
| --- | --- |
| `0x06031186` | 앞선 `RTS 0x060310D4` 이후 ~ `RTS 0x06031210` |
| `0x0603142A` | 앞선 `RTS 0x06031318` 이후 ~ `RTS 0x06031556` |
| `0x0603455C`~`0x06034752` | 리소스 665의 5×7 프레임을 갱신하는 PNT 처리 함수, `RTS 0x0603478A`까지 |
| `0x0603484E` | `0x0603478C` 이후 ~ `RTS 0x06034A42` |
| `0x06031E30` | 앞선 `RTS 0x06031D64` 이후 ~ `RTS 0x06031EBE` |

이 함수들은 리소스 로드, 좌표 계산, 여러 하위 함수 호출이 섞인 상위 UI 처리 코드다. `0x0603455C` 묶음은 후속 분석에서 `0x0609AC30`의 32-bit PNT를 `0x25E40E24`로 복사하는 경로로 확인됐다. 자세한 내용은 `11-vdp2-pnt-source-and-graphic-container.md`를 참조한다.

## VDP2 영역 사용량

대표 base의 `MOV.L @(disp,PC)` 참조 수:

| 주소 | 참조 수 | 해석 |
| ---: | ---: | --- |
| `0x25E40000` | 46 | 광범위한 VDP2 VRAM base |
| `0x25E44000` | 16 | 별도 pattern/map bank 후보 |
| `0x25E40E00` | 2 | 고정 UI/PNT 영역 후보 |
| `0x25E40E24` | 5 | 같은 PNT 안의 세부 위치 후보 |
| `0x25E41E00` | 1 | 별도 화면/창 영역 후보 |
| `0x25E420A0` | 1 | 별도 UI map 위치 후보 |

`0x25E40000`과 `0x25E44000`은 초기화·화면 전환·그래픽 로딩 전반에서 사용되므로 텍스트 전용으로 볼 수 없다. 세부 offset과 실제 화면 갱신 시점을 결합해야 한다.

## 리소스 152 후보

상위 코드 `0x06036388`에서 PC-relative word `0x0098`을 `R4`로 읽고, 단일 리소스 로더 `0x0602E724`를 호출한다.

```text
0x06036386  MOV.L ...,R5      ; 0x060BAC30
0x06036388  MOV.W ...,R4      ; 152
0x0603638A  MOV.L ...,R0      ; 0x0602E724
0x0603638C  JSR   @R0
```

따라서:

```c
load_resource(152, (void *)0x060BAC30);
```

리소스 152:

| 항목 | 값 |
| --- | ---: |
| 섹터 | 3,780..3,790 |
| 파일 `1` offset | `0x762000` |
| 할당 크기 | `0x5000` |
| entropy | 약 5.996 bits/byte |
| 고유 byte 값 | 214개 |
| zero byte | 3,850 / 20,480 |

첫 bytes:

```text
00 00 00 FF 00 00 01 03 01 00 FF 01 03 00 FE FE
FE FC FC FC FC FC FC FC FC FD FD FF 00 01 03 02
```

정형성과 반복은 있지만 raw 1bpp/4bpp 글리프라고 확정할 수 있는 배치는 아직 확인되지 않았다. `0x060BAC30`에서 소비하는 후속 함수와 시각화가 필요하다. 현재는 폰트/문자 그래픽 후보 중 하나로만 유지한다.

### `0x060BAC30` 소비자

버퍼 주소의 `MOV.L @(disp,PC)` 참조는 여섯 곳이다.

```text
0x06033F6C
0x06034034
0x06034510
0x0603457E
0x06036386  ; resource 152의 destination 설정
0x060363B6
```

`0x06034510`과 `0x0603457E`는 PNT 후보 `0x25E40E24`를 여러 번 참조하는 `0x060345xx~0x060347xx` 함수 안에 있다. 처음에는 이를 동일한 데이터 경로로 보았으나 후속 분석에서 반증됐다. 큰 상위 함수 안에 화면 처리와 사운드 스트림 처리가 함께 있었을 뿐이다.

```text
resource 152
  → Work RAM 0x060BAC30
  → 0x0601AEAC
  → SCSP sound RAM 0x05A6C000..0x05A6FFFF
```

또한 로드 직후 `0x060363B6`에서 `0x0601B00C(0x060BAC30, 5, 0)`을 호출한다. 후속 분석에서 `R5=5`는 `0x1000`-byte 블록 수로 확인됐다. 리소스 크기 `0x5000`과 정확히 일치한다. 자세한 내용은 `10-audio-stream-ring-buffer.md`를 참조한다.

따라서 리소스 152는 폰트 후보에서 제외한다. VDP2 PNT 후보 자체는 유효하지만 다른 source 포인터를 다시 추적해야 한다.

## BIOS 폰트 대신 자체 데이터일 가능성

현재 근거:

- 표준 CP932 UI 문자열이 디스크에서 발견되지 않았다.
- 자연스러운 Shift-JIS 평문도 발견되지 않았다.
- 그래픽성 리소스와 VDP2 직접 접근 코드가 매우 많다.
- 별도 Work RAM 주소로 로드되는 중간 크기 정형 데이터가 존재한다.

따라서 문자 표시가 `고유 코드 또는 토큰 → 자체 글리프/타일 → VDP2/VDP1` 경로일 가능성을 우선한다. 하지만 UI 문구 전체가 이미지인 경로와 대화 본문 렌더러가 별도로 존재할 수도 있다.

## 아직 확정하지 않은 것

- 대화 텍스트가 VDP1인지 VDP2인지
- VDP2라면 NBG0~NBG3 중 어느 레이어인지
- 위 PNT 후보 주소가 대화창인지 메뉴/전투 UI인지
- 리소스 152와 무관한 실제 폰트 source가 어디에 있는지
- 문자 코드 단위가 8-bit인지 16-bit인지
- 글리프 크기와 bpp

## 다음 조사 순서

1. 리소스 152를 제외하고 VDP2 PNT store에 도달하는 실제 source 포인터를 찾는다.
2. `0x0603455C` 묶음에서 최종 `MOV.W` VRAM store가 있는 하위 함수를 찾는다.
3. VDP2 PNT 값에 적용되는 mask/shift 상수를 확인해 character number 비트 수를 계산한다.
4. 에뮬레이터에서 대화창 표시 중 VDP 레이어 토글 및 `0x25E4xxxx` write breakpoint로 정적 후보를 검증한다.
