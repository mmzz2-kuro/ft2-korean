# Raw 글꼴 검색과 PNT 후보 제거

## 목적

확정 그래픽 컨테이너 241개를 제외한 일반 리소스에서 고정 크기 글리프 배열을 검색하고, 앞서 남겨 둔 VDP2 PNT 주소 후보가 문자 출력 경로인지 확인한다.

검사한 기계적 해석:

- 1bpp: 8×8, 8×16, 16×16
- 2bpp: 8×8, 16×16
- 4bpp: 8×8, 16×16
- 8bpp: 8×8, 8×16

## 결론

현재까지 **독립적인 raw 일본어 글꼴 리소스는 확인되지 않았다**.

계량 검색은 많은 후보를 만들었지만 상위 후보를 실제 타일로 펼치면 다음과 같은 비그래픽 자료였다.

- 수직 bar와 작은 값이 반복되는 계수·파형·상태 테이블
- 압축 또는 구조화 데이터의 우연한 저색상 해석
- 서로 다른 레코드를 임의의 타일 크기로 잘라 생긴 잡음

또한 남아 있던 세부 PNT 주소 `0x25E40E00`, `0x25E41E00`, `0x25E420A0`도 범용 그래픽 컨테이너의 tilemap 복사·생성 경로로 연결됐다. 현재 확인된 세부 PNT 주소들은 글꼴의 직접 증거가 아니다.

## Raw 후보 점수 방식

각 리소스를 여러 bpp와 셀 크기로 나눠 다음 값을 계산했다.

- 전체 tile 수
- 사용된 pixel 값 수
- 전부 0인 tile 비율
- 고유 tile 비율
- 0이 아닌 pixel 밀도
- 행 안에서 0/비0 상태가 바뀌는 비율

글꼴 후보는 일반적으로 다음 특성이 있을 것으로 가정했다.

- 64개 이상의 셀
- 획이 배경보다 적은 중간 pixel 밀도
- 공백 glyph 또는 sector padding에 따른 일부 빈 셀
- 제한된 색상 수
- 문자 획에 따른 적당한 수평 edge 빈도

그러나 2bpp나 1bpp 해석은 임의의 바이트열도 색상 수 조건을 자동으로 만족하므로 오탐이 매우 많았다. 이 점수는 후보 순서 결정에만 사용해야 한다.

## 스캔 결과

확정 그래픽 컨테이너 241개를 제외하고 점수 8 이상인 `(리소스, 해석 모드)` 조합은 17,821개였다. 한 리소스가 여러 모드에서 중복 집계되므로 리소스 수와 같지 않다.

## `0x25E40E00` 경로

초기화 코드 `0x06031154` 이후 다음 흐름이 확인된다.

```text
graphic resource
  → 0x0602F490 build_pnt
  → Work RAM staging
  → 0x0601107C copy_pnt_rect
  → 0x25E40E00
```

`0x06031186` 호출의 주요 인자:

- source: `0x0607AE60`
- destination: `0x25E40E00`
- source stride: 40 entries
- rows: 13
- width: 40 entries

`0x0603142A` 경로도 source를 `0x0607AE60 + 계산 offset`으로 만들고 같은 `0x0601107C`를 호출한다. 이는 큰 그래픽 PNT의 화면 전환/스크롤 갱신이다.

## `0x25E41E00` 경로

`0x0603481E`에서 리소스 ID `0x029B`(667)를 적재해 `0x25E40000` PNT를 만들고 팔레트를 등록한다. 이어 ID `0x029C`(668)를 적재한 뒤 다음 호출을 수행한다.

```c
build_pnt(resource_668, 0x25E20000, 0x25E41E00);
```

따라서 `0x25E41E00`은 그래픽 리소스 668의 PNT 목적지다.

## `0x25E420A0` 경로

`0x06031E0C` 이후 여러 그래픽 컨테이너 포인터를 가져와 `0x0602F490`을 연속 호출한다.

```text
pattern 0x25E00000 → PNT 0x25E40000
pattern 0x25E60000 → PNT 0x25E44000
pattern 0x25E14000 → PNT 0x25E48000
pattern 0x25E24000 → PNT 0x25E420A0
```

마지막 주소도 별도 그래픽 레이어·패널의 PNT 생성 위치이며 문자 렌더러로 볼 근거는 없다.

## 도구

전수 계량 검색:

```powershell
node scripts/ss-fs2-scan-raw-fonts.js `
  "ss/others/Farland Saga - Toki no Michishirube (Japan) (Track 1).bin"
```

- `output/ss-fs2-raw-font-candidates.json`

```powershell
  "ss/others/Farland Saga - Toki no Michishirube (Japan) (Track 1).bin" `
  4174 4bpp-8x8
```

## 조사 방향 정정

디스크에서 글꼴처럼 보이는 큰 raw bitmap을 찾는 방식만으로는 더 이상 효율이 높지 않다. 다음 우선순위는 실행 코드에서 **문자 하나를 소비하는 루틴**을 먼저 찾는 것이다.

1. 8-bit 또는 16-bit 코드값을 범위 비교하는 루프
2. 코드값을 8×8/16×16 byte offset으로 곱하는 연산
3. 대화창용 Work RAM 또는 VDP pattern 영역에 작은 사각형을 반복 기록하는 함수
4. 줄바꿈·문자 간격·커서 위치를 갱신하는 상태 변수
5. 해당 루틴이 참조하는 실제 font cache/source

그래픽에 합성된 UI 문구와 동적 대화 본문을 분리해 조사한다.

## 미확정 사항

- 대화 본문이 디스크 글꼴을 쓰는지, 런타임 생성 cache를 쓰는지
- 문자 코드 단위와 제어 코드
- VDP1과 VDP2 중 대화 본문을 담당하는 장치
- 글꼴이 일반 리소스 0..4334 밖의 대형 범위 리소스에 있는지
