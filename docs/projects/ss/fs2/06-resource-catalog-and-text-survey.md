# 세가 새턴판 파랜드 사가 2 리소스 카탈로그와 텍스트 예비 조사

## 범위

단일 리소스 로더 `0x0602E724`의 상위 호출부에서 정적 리소스 ID를 추출하고, PS1판에서 알려진 ID와 비교한다. 또한 컨테이너 전체의 평문 Shift-JIS 가능성을 예비 조사한다.

## 리소스 조회 도구

`ss-fs2-scan-container.js`에 `--ids` 옵션을 추가했다. 실행 파일 `0`의 big-endian 섹터 테이블과 Track 1 BIN의 파일 `1` 데이터를 직접 결합한다.

```powershell
node scripts/ss-fs2-scan-container.js `
  "ss/others/Farland Saga - Toki no Michishirube (Japan) (Track 1).bin" `
  --limit 1 `
  --ids "0-30,309-326"
```

각 ID에 대해 다음을 출력한다.

- 시작/끝 섹터
- 파일 `1` 내부 offset
- 할당 크기
- `be-hdr`, `raw-0x400`, `zero-prefix`, `other` 1차 판정
- 첫 32 bytes

분류는 후보 생성용이다. 특히 `other`는 하나의 실제 포맷을 뜻하지 않는다.

## 초기 공통 리소스

SS판과 PS1판은 리소스 0~22의 할당 영역이 byte-for-byte 동일하다.

| ID 범위 | 1차 형식 | 특징 |
| --- | --- | --- |
| 0~2 | `be-hdr` | 서로 다른 크기의 초기 팔레트/그래픽성 블록 |
| 3~10 | `be-hdr` | 유사한 헤더와 팔레트성 시작 데이터가 반복되는 그래픽 계열 |
| 11 | `be-hdr` | 작은 팔레트/그래픽성 블록 |
| 12~22 | `be-hdr` | `40×30` 계열 필드가 반복되는 그래픽성 블록 |

리소스 23에서 두 플랫폼이 처음 갈라진다. SS판 23~30은 모두 `00 00 04 00`으로 시작하는 `raw-0x400` 계열이고 PS1판과 크기도 다르다.

## 로더 호출부의 정적 ID

`0x0602E724` 주소를 literal pool에서 읽고 `JSR`하는 호출부 앞의 `MOV.W @(disp,PC),R4`를 역추적했다. 이 방식으로 직접 확인된 ID는 다음과 같다.

```text
152, 185, 210, 224, 259,
512, 639, 640, 641, 643, 644,
692, 694, 696, 715, 960,
1034, 1035, 1074, 1084, 1087,
4163
```

대표 호출과 SS 리소스 판정:

| 호출 주소 | ID | SS 할당 크기 | SS 1차 판정 |
| ---: | ---: | ---: | --- |
| `0x0601A262` | 259 | `0x13800` | `be-hdr(40,30,0x12C10,0xB70)` |
| `0x0601AAf0` | 210 | `0x800` | 구조체/명령열 후보 |
| `0x0601AC2A` | 185 | `0x62000` | 플랫폼 전용 대형 데이터 후보 |
| `0x0601B270` | 640 | `0x3800` | big-endian 수치 배열 후보 |
| `0x0601FB66` | 639 | `0x800` | 16-bit 색상/팔레트성 데이터 후보 |
| `0x0601FBB0` | 643 | `0x15000` | 압축 또는 인덱스 데이터 후보 |
| `0x0601FBD0` | 644 | `0x2000` | offset/명령 테이블 후보 |
| `0x060193F6` | 1074 | `0x7800` | `be-hdr(64,30,0x66D0,0xF10)` |
| `0x06013406` | 1084 | `0x1800` | `be-hdr(23,7,0x1210,0x154)` |
| `0x060196FE` | 1087 | `0xB000` | `be-hdr(64,18,0xA590,0x910)` |
| `0x06022BC6` | 4163 | `0x800` | 16-bit 색상/테이블 후보 |

`R4`가 다른 레지스터 또는 메모리에서 오는 동적 호출은 이 목록에 포함하지 않았다.

## PS1 ID를 그대로 사용할 수 없는 이유

리소스 0~22는 동일하지만 23부터 섹터 경계와 내용이 달라진다. 같은 숫자의 대표 비교:

| ID | PS1판 | SS판 |
| ---: | --- | --- |
| 152 | `VAGp` 오디오 | `00 00 00 FF...`로 시작하는 `other` |
| 185 | `VAGp` 오디오 | `0x62000` 플랫폼 전용 데이터 |
| 210 | `VAGp` 오디오 | `0x800` 구조체/명령열 후보 |
| 224 | `VAGp` 오디오 | offset table 형태의 `0x1B000` 블록 |
| 639 | `be-hdr` 그래픽 | `0x800` 16-bit 데이터 |
| 692/694/696 | 작은 `be-hdr` 그래픽 | 서로 다른 SS 데이터/그래픽 블록 |
| 1074 | PS1 1bpp UI mask 후보 | SS `be-hdr(64,30,...)` 그래픽 |

결론:

- PS1 문서의 ID 이름과 용도를 SS판에 숫자만으로 이식하면 안 된다.
- 공통 자산 비교는 내용 해시 또는 헤더/화면 대응으로 해야 한다.
- SS 실행 파일의 호출부와 런타임 목적지 주소가 해당 ID 의미의 우선 근거다.

## PS1 스크립트 구간 대조

PS1판에서 중요했던 두 구간을 SS판에서 확인했다.

### ID 309~326

- 대부분 `0x800` 할당의 작은 big-endian 구조체 배열이다.
- PS1판의 `0x0502` entry table 기반 이벤트 스크립트와 시작 구조가 다르다.
- 따라서 SS판 대사 스크립트 뱅크로 간주하지 않는다.

> 후속 조사 정정: 동일 ID 비교 결과는 맞지만 실제 SS 스크립트 뱅크는
> `278~295`에 있다. 이 범위는 PS1 `309~326`과 18개 모두 byte-for-byte
> 동일하며, SS 실행 파일 `0x0601FA30`의 리소스 ID 테이블에서도 확인된다.
> 자세한 내용은 `16-script-resource-identification.md`를 참조한다.

### ID 4277~4334

- 전부 `0x3000` 고정 할당이다.
- 대다수는 첫 32 bytes가 0으로 시작하지만, `0x400` 표본 전체를 검사하면 뒤쪽에 값이 있어 빈 블록은 아니다.
- 일부 ID `4279`, `4325`, `4327`, `4333`에 반복 패턴 데이터가 있다.
- PS1판의 `4277 + scriptWord` 메시지 뱅크 구조가 SS판에는 그대로 존재하지 않는다.

## Shift-JIS 스트리밍 스캔

도구:

```powershell
node scripts/ss-fs2-scan-sjis.js `
  "ss/others/Farland Saga - Toki no Michishirube (Japan) (Track 1).bin" `
  --limit 100 --min-japanese 6 --min-kana 4
```

도구는 448,993,280-byte 컨테이너를 추출하지 않고 모든 2,048-byte user data sector를 순회한다. Shift-JIS lead/trail 규칙을 만족하는 연속열을 디코드하고 일반 리소스 ID를 함께 출력한다.

결과:

- 출력 대부분이 그래픽/압축 데이터가 우연히 Shift-JIS 조건을 만족한 오탐이다.
- 동일한 가짜 문자열 패턴이 여러 그래픽성 리소스에서 반복된다.
- 자연스러운 조사, 어미, 문장부호를 가진 일본어 문장은 확인되지 않았다.
- 따라서 컨테이너 전체에 평문 Shift-JIS 대사가 저장되었다는 근거는 없다.

추가로 다음 UI 문자열의 표준 CP932 byte sequence를 Track 1 전체에서 정확히 검색했으나 모두 발견되지 않았다.

```text
ファーランドサーガ
はじめから
つづきから
コンティニュー
セーブ
ロード
```

이 음성 결과가 곧 모든 문자열이 고유 인코딩이라는 뜻은 아니다. UI 문구가 이미지로 저장되었거나, 대사가 압축/토큰화/16-bit 자체 코드로 저장되었을 가능성이 남는다.

## 현재 판정

1. SS판은 PS1판과 컨테이너 로더 형식을 공유하지만 리소스 ID 배치는 23부터 독립적이다.
2. 동일한 리소스 ID는 직접 대응하지 않지만, 스크립트 뱅크는 SS에서 31칸 앞당겨진 `278~295`로 확인됐다.
3. 평문 Shift-JIS 전역 스캔은 대사 탐색 방법으로 유효하지 않다.
4. 다음 텍스트 조사는 실행 파일의 문자 출력 루틴과 16-bit 코드 소비자를 먼저 찾아 역방향으로 진행해야 한다.
5. SS판 `be-hdr` 리소스는 SH-2 big-endian 환경에서 별도 endian 후처리 없이 사용될 가능성이 높다.

## 다음 조사 순서

1. 실행 파일에서 VDP1/VDP2 VRAM 및 CRAM 주소 리터럴 참조를 조사한다.
2. BIOS 폰트 함수 또는 문자 코드→글리프 변환 루틴 후보를 찾는다.
3. 화면 문자열 렌더러의 입력 버퍼를 역추적해 원본 리소스/range까지 연결한다.
4. 리소스 로더 호출부의 목적지 주소를 추적해 그래픽, 스크립트, 사운드 분류를 늘린다.
5. 에뮬레이터 RAM dump가 확보되면 일본어 대사 화면 전후 메모리 차이로 후보를 좁힌다.
