# 세가 새턴판 파랜드 사가 2 실행 파일 분석

## 범위

ISO 파일 `0`의 SH-2 코드에서 리소스 섹터 테이블을 사용하는 함수와 호출 지점을 조사한다. 파일 `0`은 별도 실행 헤더가 없는 raw binary이며 base address `0x06010000`을 사용한다.

재현 명령:

```powershell
node scripts/ss-fs2-scan-exe-xrefs.js `
  "ss/others/Farland Saga - Toki no Michishirube (Japan) (Track 1).bin"
```

도구는 ISO 파일 `0`을 디스크에 복사하지 않고 LBA 21에서 직접 읽는다. SH-2의 `MOV.L @(disp,PC),Rn`, `JSR @Rn`, `BSR` 패턴을 이용해 주소 리터럴과 호출 후보를 연결한다.

## 리소스 테이블 주소 참조

리소스 섹터 테이블 `0x0602AE9C`를 직접 읽는 명령은 네 곳이다.

| 명령 주소 | 소속 함수 후보 | 용도 후보 |
| ---: | ---: | --- |
| `0x0602E66C` | `0x0602E612` 부근 | 테이블 또는 로더 상태 초기화/변환 |
| `0x0602E708` | `0x0602E700` | 리소스 할당 크기 계산 |
| `0x0602E73E` | `0x0602E724` | 리소스 시작 섹터를 이용한 로드 |
| `0x0602E808` | `0x0602E7EC` | 복합 로드/전송 래퍼 |

첫 번째 함수의 정확한 시작 주소는 아직 미확정이다. 앞선 `RTS`가 file offset `0x1E60E`에 있지만, 분기 대상과 prologue를 더 확인해야 한다.

## `0x0602E700`: 리소스 크기 계산

이 함수는 매우 짧으며 file offset `0x1E700`부터 `RTS`가 있는 `0x1E71C`까지 이어진다.

확인된 동작:

1. 입력 리소스 인덱스를 2배 하여 u16 테이블 byte offset으로 만든다.
2. `table[id]`와 `table[id + 1]`을 읽는다.
3. 두 섹터값의 차이를 계산한다.
4. shift/add 조합으로 차이를 2,048배 한다.
5. 결과를 반환한다.

의사 코드:

```c
uint32_t resource_allocated_bytes(uint16_t id) {
    return (resource_sector[id + 1] - resource_sector[id]) << 11;
}
```

현재 단계에서는 16-bit wrap이 일어나는 후반 대형 구간을 이 함수가 직접 처리한다고 보지 않는다. 일반 리소스 ID 경로에 쓰이는 함수일 가능성이 높다.

호출 특성:

- 함수 주소 리터럴 19개를 확인했다.
- 그중 18개는 20바이트 이내의 `JSR`과 연결된다.
- 타이틀, 전투, 이벤트 등 여러 상위 코드가 공통으로 사용하는 범용 함수로 보인다.
- 직접 `BSR` 호출은 없고 주소 리터럴을 통한 간접 `JSR` 방식이다.

대표 호출 주소:

```text
0x0601B18E
0x0601D518
0x06027802
0x060301F6
0x060309D2
0x060328E8
0x06036080
```

## `0x0602E724`: 일반 리소스 로드 함수

함수는 file offset `0x1E724`의 레지스터 저장 prologue로 시작하고 `0x1E784`의 `RTS`로 끝난다.

현재 확인된 특징:

- `0x0602E700`을 내부에서 호출한다.
- 섹터 테이블에서 리소스 시작값을 읽는다.
- 함수 주소를 읽는 `MOV.L` 참조가 55개 발견됐다.
- 대부분 바로 뒤의 `JSR`로 연결되며 실행 파일 전역에서 폭넓게 호출된다.

따라서 현재는 `resource_load(id, destination, ...)` 계열의 핵심 함수로 분류한다. 정확한 인자 레지스터와 CD FAD 변환은 후속 분석에서 확정한다.

대표 호출 주소:

```text
0x06012F6A
0x06013022
0x0601413A
0x06018286
0x0601A262
0x0601D2F8
0x06021FE4
0x060300D2
0x060334DA
0x06040A3C
```

## `0x0602E7EC`: 복합 로드 래퍼

`0x0602E7DC`부터 `0x0602E7EA`까지는 앞 함수의 literal pool이다. 다음 함수의 실제 prologue는 file offset `0x1E7EC`, RAM `0x0602E7EC`에서 시작한다.

확인된 특징:

- 다수의 보존 레지스터를 스택에 저장한다.
- 테이블에서 시작 섹터를 읽는다.
- `0x0602E700`과 `0x0602E724` 주소가 직전 literal pool에 함께 있다.
- 함수 주소를 직접 참조하는 상위 호출점은 현재 `0x060278C2` 한 곳이다.

이 함수는 여러 리소스를 연속 처리하거나 추가 메타데이터를 적용하는 상위 래퍼일 가능성이 있다.

## 호출 방식에 대한 결론

리소스 함수는 가까운 코드에서 `BSR`로 호출하기보다 다음 패턴을 주로 사용한다.

```text
MOV.L @(disp,PC), Rn   ; literal pool에서 함수 주소 로드
JSR   @Rn
<delay slot>
```

따라서 이후 교차 참조 도구는 SH-2 `BSR` 검색만으로는 부족하다. PC-relative literal pool을 먼저 해석하고, 그 값을 소비하는 `JSR @Rn`까지 연결해야 한다.

## 후반 테이블 개수

`0x0602E620` 초기화 함수에서 일반 리소스/range pair 경계를 구분하는 상수와 wrap 보정 loop를 확인했다.

- 일반 리소스: 4,335개, ID 0~4,334
- 후반 range pair 시작 index: 4,335
- range pair: 17개
- wrap 보정 단위: `0x10000`섹터

실제 범위는 `03-resource-map.md`에 기록했다.

## 다음 분석 순서

2. CD block/FAD 변환 상수 `150`과 파일 `1` 시작 LBA `178`의 사용점을 찾는다.
3. 리소스 ID 상한 검사와 후반 range pair 반복 횟수를 찾는다.
4. 대표 호출부에서 상수 리소스 ID를 역추적해 화면 장면과 연결한다.
5. 로더가 데이터를 적재하는 RAM 영역과 후처리 함수를 분리한다.
