# 문자 소비 루프 탐색

## 목적

앞선 raw 글꼴 검색에서 독립적인 일본어 글꼴 atlas를 찾지 못했으므로, 이번 단계에서는 실행 파일에서 문자열을 한 글자씩 읽는 루프를 역으로 찾았다. 목표는 다음 형태의 루틴을 식별하는 것이다.

1. `MOV.B @Rm+,Rn` 또는 `MOV.W @Rm+,Rn`으로 문자 코드를 순차 소비한다.
2. NUL, 개행, 제어 코드 또는 SJIS 범위를 판정한다.
3. 문자값을 글리프 번호나 패턴 주소로 변환한다.
4. Work RAM, VDP1 command, VDP2 PNT 또는 패턴 캐시에 결과를 기록한다.

## 결론

정적 휴리스틱이 찾은 33개 후보 중 **대사 문자 디코더로 확정할 수 있는 루프는 없었다**.

- 즉시값 종료문자를 비교하는 후보는 0개였다.
- 상위 점수 후보는 타일맵을 16-bit 단위로 읽어 32-bit PNT에 전개하는 그래픽 루프였다.
- 여러 후보는 `memcpy` 계열, 고정 길이 수치 테이블, 색 변환 테이블이었다.
- `0x0605A070`에서 NUL을 인식하는 `strncpy`형 범용 함수가 확인됐지만, 유일한 정적 호출처는 12바이트 고정 레코드 복사 경로였다.
- 실행 파일 안에서 표준 SJIS 경계값을 직접 비교하는 흔적도 찾지 못했다.

따라서 현재 증거는 본문이 실행 파일 내부의 평문 SJIS 문자열이거나, 단순한 NUL 종료 문자열을 곧바로 글리프로 바꾸는 구조라는 가설을 지지하지 않는다. 문자열/스크립트가 별도 리소스에 있고 명령 스트림 해석 과정에서 간접 디스패치될 가능성을 우선 조사해야 한다.

## 자동 탐색 방법

새 도구 `scripts/ss-fs2-scan-text-loops.js`는 Track 1의 LBA 21에서 실행 파일 319,524바이트를 추출하고 다음 조건을 검색한다.

- SH-2 `MOV.B @Rm+,Rn` 또는 `MOV.W @Rm+,Rn`
- 이후 40바이트 안에 현재 위치 부근으로 돌아가는 조건 분기
- 비교, 메모리 기록, 즉시값 종료문자 판정 여부

실행:

```powershell
node scripts/ss-fs2-scan-text-loops.js `
  "ss/others/Farland Saga - Toki no Michishirube (Japan) (Track 1).bin"
```

결과는 33개 후보였다. 이 검사는 후보 누락을 허용하는 휴리스틱이며, 간접 점프 디스패처나 인덱스 기반 읽기는 검색 대상에 포함되지 않는다.

## 주요 후보 판별

| 주소 | 읽기 | 판별 결과 |
| --- | --- | --- |
| `0x060231D4` | 16-bit | 32×26 계열 중첩 루프에서 타일 번호를 32-bit PNT 값으로 전개 |
| `0x0602327E` | 16-bit | 40×30 계열 중첩 루프, 위 루틴과 같은 그래픽 전개 계열 |
| `0x060233A4` | 16-bit | 가변 폭·높이 타일맵을 PNT로 복사 |
| `0x0602F502` 등 | 16-bit | 그래픽 컨테이너 PNT 생성기의 크기별 분기 |
| `0x06010AE2` | 8-bit | 비트 마스크와 shift를 사용하는 픽셀/비트 변환 |
| `0x060110FC` | 8-bit | 행당 `0x40`바이트를 복사하며 0 값을 건너뛰는 그래픽 블록 처리 |
| `0x0602A134`, `0x0602A3E6`, `0x0602A668` | 16-bit | 길이 필드와 좌표 오프셋을 적용하는 구조화 테이블 전개 |
| `0x06033582` | 16-bit | 40개 값을 `0x25E5C000`에 32-bit 단위로 기록하는 VDP 영역 전송 |
| `0x0603FFB2` | 8-bit | 세 입력 lookup 결과를 조합해 16-bit 값을 만드는 색/픽셀 변환 |
| `0x06059F88` | 8-bit | 길이 기반 범용 메모리 복사 |
| `0x0605A07C` | 8-bit | NUL 또는 최대 길이에서 멈추고 나머지를 0으로 채우는 `strncpy`형 함수 |

상위 후보 `0x060231D4`와 `0x0602327E`는 문자 코드 소비처럼 보였지만, 각각 내부 반복 한계가 31/39이고 출력 포인터가 4바이트씩 증가한다. 이미 확인한 그래픽 컨테이너의 16-bit tilemap을 VDP용 32-bit 값으로 확장하는 루프와 일치한다.

## NUL 인식 루틴 `0x0605A070`

루틴의 핵심 동작은 다음과 같다.

```text
R4 = destination
R5 = source
R6 = maximum length

copy byte
stop when byte == 0 or R6 == 0
fill remaining destination bytes with 0
```

이는 문자 인코딩을 해석하지 않는 범용 고정 길이 문자열 복사 함수다. 실행 파일 xref 결과는 다음과 같다.

- 함수 주소 literal: 실행 파일 offset `0x3396C`
- 호출 명령: `0x0604392E`
- 호출 시 최대 길이: `R6 = 12`
- 호출 주변에서는 24바이트 stride 레코드를 순회하고 여러 12바이트 필드를 비교·복사한다.

이 경로에는 SJIS lead/trail byte 판정, 글리프 주소 계산, VDP 기록이 없다. 이름이나 짧은 레코드 문자열일 가능성은 남지만 대사 렌더러의 증거는 아니다.

## SJIS 상수 교차 검사

실행 파일의 PC-relative 16-bit literal 참조에서 다음 대표값을 검사했다.

- `0x8140`, `0x817F`, `0x8180`: SJIS 기호 영역 주변
- `0x829F`, `0x82F1`: 히라가나 영역 주변
- `0x889F`, `0x9872`: 제1수준 한자 영역 주변
- `0x9FFC`, `0xE040`, `0xEBBF`: lead/trail 및 상위 영역 경계 후보
- `0x000A`, `0x000D`: LF/CR

해당 값의 `MOV.W @(disp,PC)` 참조는 모두 0개였다. `0xFFFF` 참조는 있었지만 객체 슬롯과 상태 구조의 미사용 sentinel로 분류됐다. 상수 부재만으로 SJIS를 배제할 수는 없으나, 메인 실행 파일에 전형적인 범위 비교형 SJIS 디코더가 있을 가능성은 낮아졌다.

## 해석상의 제한

- 디코더가 `MOV.B @Rm,Rn` 뒤에서 포인터를 별도로 증가시키면 이번 검색에서 누락될 수 있다.
- 문자 클래스 판정을 lookup table로 수행하면 SJIS 경계 상수가 코드에 나타나지 않는다.
- 스크립트 VM이 opcode jump table을 사용하면 짧은 기본 블록만 존재해 backward branch 휴리스틱에 잡히지 않는다.
- 실제 문자열이 압축되어 있다면 압축 해제 후 RAM에서만 문자 소비 루프가 관찰될 수 있다.
- BIOS 또는 별도 라이브러리 경로 사용 여부는 이번 결과만으로 확정할 수 없다.

## 다음 조사 방향

다음 단계는 실행 코드에서 글꼴을 바로 찾는 대신 리소스의 **스크립트형 구조**를 먼저 좁힌다.

1. 그래픽·오디오로 확정된 리소스를 제외한다.
2. 나머지 리소스에서 반복되는 opcode, offset table, 레코드 경계를 계량한다.
3. 동일 계열 리소스의 공통 header와 포인터 규칙을 찾는다.
4. 해당 리소스 ID를 요청하는 loader 호출처와 상태 디스패처를 연결한다.
5. 디스패처 내부의 byte/word 소비 코드를 기준으로 문자 코드와 제어 코드를 분리한다.

이 순서라면 압축·고유 인코딩·스크립트 VM 중 어느 구조인지 먼저 결정한 뒤 글꼴과 렌더러 경로를 다시 추적할 수 있다.
